\begin{abstract}
Test-Driven Development (TDD), born in the early 2000s, treats the test as a runnable
specification: write the test first, then only the code needed to pass it. Agentic software
engineering today rediscovers that loop at machine speed. An LLM writes tests for a
natural-language specification, an LLM writes code against the specification, LLM-as-a-judge
reviewers gate each step, and the pipeline reports success once its code passes its own tests.
The only way TDD could guarantee this is if a human could understand precisely what the
specification intended. When models write the tests and code, nothing in the loop checks if the
tests mean what the specification says. We call this failure mode the \emph{verification gap}:
problems a pipeline reports as solved fail held-out benchmark tests that the pipeline never
sees. We measure an instrumented TDD pipeline on two benchmarks, HumanEval and a LiveCodeBench
window published after the generating model's training cutoff. The gap is systematic. When a single
cheap model writes the tests, writes the code, and judges both, about one reported success in
four is false, and every wrong one has
the same signature: tests and code that agree with each other but not with the specification.
We then test the remedy builders reach for: a frontier model as the test author or the
LLM-as-a-judge reviewer. The upgrade drives the efficiency of the loop. Wrongly rejected correct
solutions go to zero and on the unseen problems the frontier reviewer's feedback improves true
success rates by a third. The rate of false success claims, however, does not move---not under a
frontier test author or judge, and not across the three frontier verifiers we test, spanning three
providers.

Model strength inside the loop buys completeness, not soundness. The recipe and its caveat are
both concrete for builders: a cheap generator coached by a frontier reviewer is an efficient
production configuration, but its ``all tests pass'' means the code agrees with its own tests,
which is not the same as being correct, so shipping decisions still need one check from outside
the loop, such as held-out tests or differential verification.

Both benchmarks so far are single-function algorithms, whereas real applications are more
complex assemblies of interconnected entities collaborating to achieve a goal. To check that this gap is not an
artifact of the simpler code benchmarks, we replicate on \textsc{RGRBench}, a released corpus of $89$
application-scale, multi-concern Python packages whose hand-verified oracles carry measured
error bars. The gap widens at scale; the ratio of claimed successes that are failures is two in
five. The rate increases with application complexity and it gets worse as the pipeline retries
itself. A frontier judge leaves it untouched again, and three independent instruments all land
in the same range. We release all instruments, prompts, raw results, and analyses.
\end{abstract}

\section{Introduction}
\label{sec:intro}

In the early 2000s Test-Driven Development (TDD)~\cite{beck2002tdd} emerged as a way to cope
with the low quality and defect rate of code that was tested after it was written. The idea of
``Test First'' development was meant to alleviate some perceived seeds of low-quality software.
The first was to catch requirements interpretation problems as early as possible, by forcing
developers to turn them into automated tests to be agreed upon. The tests effectively become a
contract, a runnable specification for the system under development. The second was to control
the entropy of an evolving system by reducing the scope of additions and changes by bounding
them to a test. These tests are the reflection of acceptance criteria that isolate
functionality into more atomic, focused units, which leads to better understanding; a test
version of the Single Responsibility Principle (SRP), often quoted as ``do one thing and one
thing only''.

The mechanics of the process are encoded in the Red-Green-Refactor loop. A test is written
against a specification, and it fails since the supporting code does not exist. That is the
``Red'' phase. Then, and this is the critical aspect of curtailing the increasing entropy of the
system, the minimal code must be written to pass the test, no more. This is the ``Green'' phase.
The last phase, the ``Refactor'' phase, is optional, taken when the code can now be made better
with the safety net of the passing tests.

Agent pipelines now execute that loop independently and they write their own acceptance
criteria. An LLM turns a natural-language specification into a test suite, a second generation
writes code against those tests, LLM-as-a-judge reviewers affirm each step, and the pipeline
declares success when its code passes its tests. The pipeline is equipped with its own evidence.

But TDD is susceptible to misinterpretations of the requirements. Those misunderstandings are
now cemented in code that drives the pipeline. What good are passing tests if they are testing
the wrong thing? TDD practitioners already have a name for tests that reflect the code rather
than the requirement: the \emph{ugly mirror}~\cite{rudolph2008uglymirror}.

We will show that autonomous test-first pipelines plant the seeds for the ugly mirror at the
natural-language-to-test generation layer. We call the resulting discrepancy the
\emph{verification gap}: problems a pipeline claims to have solved that fail a held-out oracle
the pipeline never sees (Sec.~\ref{sec:gap}).

This paper measures that gap by stress-testing an agentic test-first pipeline. In the control
configuration, with an inexpensive, non-frontier model in every role (hereafter \emph{all-weak}), the gap is
persistent and
two-sided. Out of 30 problems per run, an average of $4.0$ reported successes fail HumanEval's
strong oracle ($18\%$ of what the pipeline claims) and $4.8$ fail the hidden oracle of a
LiveCodeBench window post-dating the generator's training cutoff ($29\%$ of claims), while
$5.4$ and $3.4$ correct implementations per run are abandoned because the pipeline's own wrong
tests vetoed them.

% trace: experiments/exp007_lcb_asymmetry/results/ANALYSIS.md (control)

The most common solution to a model misinterpreting a requirement is to use a stronger model to
write the tests. LLM-as-a-judge is also a common technique used to review the generated code at every
level. Production systems increasingly follow this asymmetric recipe: use a cheap model to
generate and a frontier model somewhere in the verification roles. The \emph{test author} turns
the specification into the test suite; the \emph{judge} reviews tests and code and analyzes
failures. We test both by swapping a frontier model into the test-author role, the judge role, and both,
against a fixed weak generator (gpt-4o-mini) on both benchmarks, and rerun the design across three
frontier verifiers spanning three providers (GPT-5.6 Terra, Gemini-2.5-Pro, Claude-4.5-Sonnet;
Sec.~\ref{sec:design}). The result is the paper's central finding:
\textbf{verification strength is asymmetric}. The false-success rate, the gap proper, does not
change in any configuration, on either benchmark, or under any of the three verifiers. False rejects
collapse under the frontier judge---to zero in every LiveCodeBench run with GPT-5.6 Terra---and on
unseen problems its feedback raises the true success rate by five to six problems in thirty
($p{\leq}.03$). It coaches the weak generator toward
better tests and better code, but it keeps its verdicts as blind as the weak judge's. A frontier
model authoring tests moves nothing at all.

\paragraph{From algorithm to application scale.} Both benchmarks above are single-function and
algorithmic, not the shape the field usually looks to, and far from the multi-file, stateful
applications production agents create. To see if this gap is just a toy-problem artifact, we
built \textsc{RGRBench}: $89$ Python packages that are stateful and multi-concern (event
sourcing, reservations, billing), across three difficulty tiers, each with a hand-verified suite
that has its own measured blind-spot rate (mutation kill rate $0.981$, every surviving mutant
classified). We ran the whole pipeline on all $89$ packages from their requirements alone,
without ever showing the tests, across $534$ runs. At this scale the gap does not narrow; it
grows. Roughly two claimed successes in five fail the held-out oracle ($41.5\%$, $95\%$ CI
$[30.4, 53.7]$), the rate keeps increasing with complexity ($31\% \to 54\% \to 86\%$ across
tiers), and it increases even more after the pipeline does its own retries ($35\%$ first attempt
versus $64\%$ multi-attempt). A third time, the frontier judge does not move it and again takes
away all false rejects. The range is consistent with the SWE-bench overfitting literature: one
in five to one in three self-test-passing patches are
wrong~\cite{ahmed2025overfitting,yu2026sweabs}, and ours is the first such rate measured on
oracles whose error is published.

\section{Background and Related Work}
\label{sec:related}

\paragraph{Weak tests overestimate, in benchmarks and pipelines alike.}
EvalPlus showed that the \emph{benchmark's} tests were the weak link in code evaluation:
extending HumanEval's suites revealed substantial previously-undetected wrong code and
reordered model rankings~\cite{liu2023evalplus}. LiveCodeBench addressed the complementary
contamination problem with rolling problem collection~\cite{jain2024livecodebench}. We used
both. EvalPlus serves as a strong oracle, and for LiveCodeBench we use a post-cutoff window as a
hidden oracle. In the TDD pipeline, when the tests are weak, the overestimation occurs inside
the loop, and the pipeline's self-assessment shows the same blindness EvalPlus documented for
benchmarks. At repository scale (whole software projects, not single functions), the same
overestimation has been measured directly:
strengthened or held-out suites reject around one in five to one in three of the patches
accepted by a benchmark's original tests~\cite{ahmed2025overfitting,yu2026sweabs}. Our
verification gap is the TDD-internal, agent-native manifestation of this result, measured
against oracles whose precision is estimated rather than assumed;
Sec.~\ref{sec:results-scale} shows that all three instruments arrive at the same range.

\paragraph{The ugly mirror.}
TDD practitioners have long referred to the failure mode of writing tests when an
implementation already exists: the \emph{ugly mirror}~\cite{rudolph2008uglymirror}, a test that
represents the code and certifies what it does rather than what it should, with the tautological
test as the limit~\cite{pereira2010ttdd}. Test-first ordering is the classic defense: with no
implementation to bend toward, the test can only represent the specification. Our subject
pipelines follow that order, and we find the mirror survives it by moving up a level. When a
model authors tests from its \emph{reading} of the specification and a similar model writes code
against them, both artifacts reflect the same misreading, and GREEN-phase generation then
ensures the code mirrors the tests. The pipeline reports that self-consistency as success, while
it only indicates that the tests and the code agree.

\paragraph{Test-first generation with LLMs.}
Providing tests alongside problem statements improves generation~\cite{mathews2024tdd}; TiCoder
makes the authorship of tests interactive, with a human validating proposed tests before code
is accepted~\cite{fakhoury2024ticoder}; TENET and TDFlow bring test-driven loops to
repository-scale agents~\cite{sun2025tenet,tdflow2025}. Along this line, tests are either
supplied, human-vetted, or evaluated end-to-end by their impact on pass rates. Our subject
class is the fully autonomous case, in which the pipeline authors both tests and code. What we
are interested in is the reliability of the pipeline's own judgement about itself, which the
end-to-end view cannot see because the benchmark oracle is outside the loop.

\paragraph{Self-generated tests as signal.}
CodeT uses generated tests to rank candidate solutions, taking agreement between generation and
testing as a signal~\cite{chen2023codet}, while ConVerTest targets ground-truth-free test
generation through consensus and cross-validation~\cite{convertest2026}. Both use agreement as
evidence of correctness. The verification gap makes the failure mode of that assumption visible:
the agreement between self-authored tests and code is exactly what our gap set gets wrong on
every one of its members. Our asymmetry experiments show that the agreement stays wrong even
when a frontier model provides either half.

\paragraph{LLM judges on code.}
Benchmarks of LLM-as-judge for coding tasks find judges only moderately aligned with the
execution outcome~\cite{jiang2025codejudgebench}, and systematic failures have been documented
when LLMs check code against natural-language specifications~\cite{verifyfailures2025}. In our
subject pipeline, judges are introduced \emph{as gates} inside the loop, backed by an execution
gate that overrides the judge's predictions. The asymmetry experiments build on those standalone
results: upgrading the judge to a frontier model makes it much more valuable as a source of
\emph{feedback}, while leaving its \emph{accept verdicts} no better than before.

\paragraph{Multi-agent code generation.}
Multi-agent SDLC frameworks report success at completing end-to-end
tasks~\cite{hong2024metagpt}; to our knowledge they do not analyze their internal quality gates
beyond ablation on pass rates. Our protocol is complementary and portable: any pipeline whose
harness can record the executed self-verdict alongside its outputs admits the same measurement.

\section{The Verification Gap}
\label{sec:gap}

\subsection{Definitions}

Consider a code-generation pipeline that, for a problem $i$ with natural-language
specification $\mathit{spec}_i$, produces an implementation $y_i$, a test suite $T_i$ that the
pipeline itself authored from $\mathit{spec}_i$, and a self-verdict
$s_i \in \{0,1\}$, the pipeline's own claim that the problem is solved, derived from running
$T_i$ against $y_i$ and from any internal quality gates (in our subject pipeline, LLM judges).
An \emph{oracle verdict} $o_i \in \{0,1\}$ is the outcome of a test suite the pipeline never
sees. We use three oracles of increasing distance from the pipeline's inputs: the
\emph{visible-adjacent oracle} $o^{\mathrm{base}}_i$ (HumanEval's original tests, which
overlap the worked examples visible in $\mathit{spec}_i$), a \emph{strong oracle}
$o^{\mathrm{plus}}_i$ (HumanEval\texttt{+}~\cite{liu2023evalplus}, whose tests exceed the
visible examples by roughly two orders of magnitude), and a \emph{hidden oracle}
(LiveCodeBench's private test sets~\cite{jain2024livecodebench}, never distributed with the
problem statement at all).

The \emph{verification gap} of a run over problems $P$ is the set
$G = \{\, i \in P : s_i = 1 \wedge o_i = 0 \,\}$: problems the pipeline believes it solved and
the oracle rejects, the \emph{false accepts}. We report it as a per-run count over $|P|$ and,
where the denominator matters, as the \emph{conditional gap} $|G| / |\{ i : s_i = 1 \}|$, the
probability that a claimed success is wrong. The complementary error set
$R = \{\, i : s_i = 0 \wedge o_i = 1 \,\}$ (\emph{false rejects}: correct code vetoed by the
pipeline's own tests) completes the picture; self-verification error runs in both directions
(Table~\ref{tab:confusion}).

\begin{table}[H]

Every element of $G$ is, by construction, a case of \emph{self-consistent misalignment}: $y_i$
satisfies $T_i$, and both jointly deviate from $\mathit{spec}_i$. The gap is therefore not a
measure of weak code generation, since those failures are caught internally. It measures the
pipeline's inability to notice a particular class of its own errors, the ones its self-authored
tests inherit. In the vocabulary of TDD practice, every gap member is an ugly
mirror~\cite{rudolph2008uglymirror} the pipeline built for itself: the tests reflect an
interpretation rather than the specification, and the implementation faithfully mirrors the
tests.

\subsection{Subject pipeline}

Our subject is a test-first multi-agent pipeline in which an LLM writes tests from the
specification (RED), an LLM judge scores the tests, a second generation step writes an
implementation against those tests (GREEN), a judge predicts test outcomes, an execution
gate then runs the tests and overrides optimistic judge predictions, and a final VERIFY phase
runs the full suite, with bounded retries and textual feedback loops
(Algorithm~\ref{alg:tdd}, Fig.~\ref{fig:loop}). The pipeline's headline configuration also
\emph{anchors} self-authored tests: prompt and judge jointly mandate that every worked example
in the specification appear as a test case verbatim. Note what the execution gate cannot do:
it validates $y$ against $T$, so a wrong $T$ passes it wrongly.

The complete instrument (engine, prompt templates, and the defect register from a
line-by-line review of the pipeline) ships with the artifact.
% trace: src/vgap/pipeline/REVIEW.md (H-1..H-15, B-1..B-10, E-1)

\begin{algorithm}[t]
\caption{Execution-gated TDD cycle (subject pipeline; generator $G$ and judge $J$ are
role-assigned per experimental cell)}
\label{alg:tdd}
\begin{algorithmic}[1]
\Require spec, test author $G_T$, code generator $G$, judge $J$, threshold $\tau$, retries $R$
\For{$r \gets 1 \ldots R$} \Comment{RED: author the tests}
  \State $T \gets G_T.\mathrm{tests}(\mathrm{spec}, f)$;\quad $q \gets J.\mathrm{score}(T, \mathrm{spec})$;\quad $f \gets J.\mathrm{feedback}$
  \If{$q \geq \tau$} \textbf{break} \EndIf
\EndFor
\If{$q < \tau$} \Return $s{=}0$ \EndIf
\For{$r \gets 1 \ldots R$} \Comment{GREEN: code against own tests}
  \State $y \gets G.\mathrm{code}(\mathrm{spec}, T, f)$;\quad $\hat{q} \gets J.\mathrm{predict}(y, T)$
  \If{$\hat{q} \geq \tau$}
    \If{$\mathrm{run}(T, y).\mathrm{allPass}$} \textbf{break} \Comment{execution gate: judge overruled by pytest}
    \Else\ $f \gets \mathrm{debugAnalysis}(T, y)$ \EndIf
  \Else\ $f \gets J.\mathrm{feedback}$ \EndIf
\EndFor
\For{$r \gets 1 \ldots R$} \Comment{VERIFY: full suite; failures route back to GREEN}
  \If{$\mathrm{run}(T, y).\mathrm{allPass}$} \Return $s{=}1,\, y,\, T$ \EndIf
  \State $f \gets J.\mathrm{analyzeFailures}(T, y)$;\quad regenerate $y$ as in GREEN
\EndFor
\State \Return $s{=}0,\, y,\, T$
\end{algorithmic}
\end{algorithm}

\subsection{Prompt architecture}
\label{sec:prompts}

Four prompts carry the loop; their structure is part of the instrument and matters to the
results, so we state it. (Skeletons in Appendix~\ref{app:prompts}; the templates ship with
the artifact under a SHA-256 manifest, with render-contract tests asserting the properties
below.)

\emph{RED generator.} Role framing (``your tests are the only specification the implementer
will see''), the task description and full specification, the scenario list, then an
\emph{anchoring block}: for every worked example in the specification, a test named
\texttt{test\_canonical\_example\_N} with the example's exact inputs and outputs and a
one-line derivation comment. Five rules follow (test only specified behavior; exact
signatures; computed expected values; import from the solution package; plain pytest). On
retries, the judge's directives and the previous attempt are appended. Output contract: one
fenced Python block.

\emph{RED judge.} Judges one question, whether the suite faithfully verifies the
specification, via ordered checks: canonical-example coverage (an anchoring block mirroring the
generator's; a missing or altered example forces the minimum score), assertion fidelity
(recompute every expected value), no invented constraints, coverage of stated behaviors, and
sanity. A deduction schedule maps findings to a score; the response must end with the exact
line \texttt{Final score: <x.xx>}, and feedback is emitted as apply-verbatim
\texttt{ADD:}/\texttt{REMOVE:}/\texttt{FIX:} directives, the feedback channel that
Sec.~\ref{sec:discussion} shows doing the work.

\emph{GREEN generator.} The tests are presented as the acceptance criterion; rules forbid
hardcoding test inputs and invented behavior; output is a single JSON object carrying the
implementation file (path, action, content). This is the one place structured output is used,
with the code as an escaped string field.

\emph{GREEN judge.} Predicts per-test PASS/FAIL by tracing the implementation against each
test, flags test-gaming in one line, and must end with \texttt{Rating: <x.xx>} (predicted
pass fraction). The execution gate then runs the tests regardless, so this judge's optimism
is bounded by pytest.

The anchoring blocks in the RED pair are delimited by explicit markers in the template
source, and the artifact's ablation variants (generator-side only, judge-side only, neither)
are excised mechanically from those markers, and the variant used in every run is asserted on
the rendered prompt at smoke time. A fifth template, the failure analyst of
Sec.~\ref{sec:gap}'s retry loops, fires whenever an execution gate or VERIFY run fails: it
traces each failing test, names the root cause, and emits \texttt{FIX DIRECTIVES:} lines the
next GREEN attempt consumes verbatim; it produces analysis only, never code.

\subsection{Measurement protocol}
\label{sec:protocol}

Three requirements make the gap measurable rather than anecdotal (Algorithm~\ref{alg:audit}).

\begin{algorithm}[t]
\caption{Verification-gap measurement over instrumented runs}
\label{alg:audit}
\begin{algorithmic}[1]
\Require pipeline $P$, problems $\mathcal{P}$, held-out oracle suites $O$, runs $N$
\For{each problem $i \in \mathcal{P}$, run $r \in 1..N$}
  \State $(y_{ir}, T_{ir}, s_{ir}) \gets P(i)$ \Comment{harness captures artifacts + the executed self-verdict}
  \State $o_{ir} \gets \mathrm{Exec}(O_i \text{ on } y_{ir})$ \Comment{standard harness (EvalPlus / LCB / RGRBench adapter), outside the loop}
\EndFor
\State $G \gets \{ (i,r) : s_{ir}{=}1 \wedge o_{ir}{=}0 \}$;\quad $R \gets \{ (i,r) : s_{ir}{=}0 \wedge o_{ir}{=}1 \}$
\State \Return $G, R$, per-run provenance and cost
\end{algorithmic}
\end{algorithm}

\emph{(1) Both verdicts measured, never reported.} The self-verdict $s_{ir}$ is an outcome the
harness observes, not a claim the pipeline makes about itself: the executed result of the
pipeline's own final test run, captured with per-call token and cost accounting. The oracle
verdict is computed on the produced implementation, outside the loop, by the benchmark's own
harness: EvalPlus~\cite{liu2023evalplus} for HumanEval, LiveCodeBench's
evaluator~\cite{jain2024livecodebench} for the hidden-test problems, and, at application scale,
RGRBench's hand-verified suites through the non-cheating adapter
(Sec.~\ref{sec:results-scale}). Every number in this paper derives from these two captured
streams---the self-verdict and the oracle---and is regenerable from committed per-run artifacts.
% trace: src/vgap/pipeline/humaneval_runner.py, lcb_runner_local.py;
% trace: experiments/exp007_lcb_asymmetry/score_lcb.py (harness-side scoring)

\emph{(2) Oracles beyond the visible examples.} Anchoring couples $T_i$ to the
specification's worked examples, which HumanEval's base oracle partially shares; a gap
measured only against $o^{\mathrm{base}}$ understates the phenomenon. On the all-weak
configuration, false accepts average $3.0$ per 30-problem run against the base oracle and
$4.0$ against HumanEval\texttt{+}.
% trace: exp006 ANALYSIS.md (control_rerun fa_base/fa_plus)
The LiveCodeBench experiment removes visibility entirely: prompts carry the statement and its
public examples, while scoring runs the private suites, on problems whose contest dates
post-date the weak model's training cutoff by more than a year.

\emph{(3) Pre-registered noise floors.} Per-problem outcomes are unstable across
byte-identical runs: the all-weak configuration disagrees with itself on $6/30$ problems (HumanEval
subset) and $9/30$ (LiveCodeBench) across five runs, with maximum pairwise pass-total
differences of $4$ and $3$.
% trace: exp006 scores/ per-run eval results; exp007 scores/ (flip counts derived in
% scripts/make_figures.py inputs; totals in each ANALYSIS.md)
Both experiments therefore fixed minimum effect sizes in advance ($4$ problems on
success-rate contrasts, $2$ on false accepts, $2$ on false rejects, $3$ on total verdict
error) that any contrast must exceed on top of statistical significance; the observed
control spreads fall at or inside these thresholds. Single-run comparisons, common in the
literature, cannot distinguish intervention effects of this size from run-to-run noise.

\section{Study Design}
\label{sec:design}

The study asks four questions.
\begin{description}
\item[\textbf{RQ1 (phenomenon).}] How large is the verification gap, against visible-adjacent,
strong, and hidden oracles, and how does it decompose into false accepts and false rejects?
\item[\textbf{RQ2 (asymmetry).}] Does a frontier model in the verification roles (as test author,
as LLM-as-a-judge reviewer, or both) close the gap?
\item[\textbf{RQ3 (mechanism).}] When a stronger verifier does help, does the improvement flow
through its \emph{verdicts} (better gatekeeping) or through its \emph{feedback} (better generation)?
\item[\textbf{RQ4 (scale).}] Do the gap's magnitude and its invariance to verifier strength survive
the move from single-function algorithms to application-scale, multi-concern programs, and how does
the gap respond to task complexity and to the loop's own refinement?
\end{description}

\paragraph{Experiments.} The model experiments share one asymmetry design with four conditions
(\emph{cells}): a weak model W (\texttt{gpt-4o-mini}) generates code in every cell; a frontier
verifier S replaces W in the test-author role, the judge role (all three judge duties), or both;
the control is W everywhere. We fill the role S with three verifiers spanning three
providers---GPT-5.6 Terra, Gemini-2.5-Pro, and Claude-4.5-Sonnet\footnote{\texttt{gpt-4o-mini} is
OpenAI's GPT-4o mini. The verifiers are OpenAI's \texttt{gpt-5.6-terra} (the mid-tier GPT-5.6 model,
released 2026-07-09; model card
\url{https://developers.openai.com/api/docs/models/gpt-5.6-terra}), Google's \texttt{gemini-2.5-pro}
(via Vertex AI), and Anthropic's \texttt{claude-sonnet-4-5}. All models are called through a LiteLLM
shim.}---and run the design on both benchmarks for each. $N{=}5$ runs per cell, $30$ problems per
run, escalation off, judge threshold and retries fixed across cells. Every experiment was
\emph{pre-registered}: hypotheses, decision rules, and budget caps were committed to the repository
before the first API call, so the analyses test predictions rather than fit them. The primary pair
uses GPT-5.6 Terra: exp006 runs a HumanEval subset enriched for previously unstable problems, scored
by both EvalPlus oracles, and exp007 replicates it on contamination-controlled ground---all $19$ easy
plus the first $11$ medium LeetCode problems from LiveCodeBench release~v6 with contest dates
$\geq$~2025-01-01, selected by a deterministic rule fixed in advance after a pilot located the weak
model's measurable band, and scored by the private LCB suites; the FR reduction and FA invariance
observed in exp006 were registered as confirmatory predictions for exp007 before its first API call.
A pre-registered replication (exp011) then reruns both benchmark designs with the two non-OpenAI
verifiers, Gemini-2.5-Pro and Claude-4.5-Sonnet, to test whether the soundness null depends on the
choice of frontier model (Sec.~\ref{sec:results-asym}).
% trace: experiments/exp006_model_asymmetry/README.md, exp007_lcb_asymmetry/README.md,
% exp011_verifier_generalization/PRE_REGISTRATION.md (pre-registrations);
% experiments/pilots/README.md (band-location pilot)

\paragraph{The application-scale experiment.} A third experiment (exp010) moves to
\textsc{RGRBench}'s $89$ packages. The pipeline receives only each package's requirements
document (user-story acceptance criteria derived from the tests alone, with the tests
themselves never shown) and is graded by the hidden hand-verified suite through a non-cheating
adapter (Sec.~\ref{sec:results-scale}). The design keeps the soundness-invariance contrast in its most
consequential form: a \emph{control} cell (weak model in every role) against a
\emph{strong-judge} cell (GPT-5.6 Terra in all judge duties), $N{=}3$ runs per package per
cell ($534$ runs). Because RGRBench labels each package by difficulty tier and the harness
records whether a claim arrived on the first attempt or only after retries, the same runs test
whether the gap scales with complexity (H-D4) and whether refinement worsens it (H-D2), both
pre-registered before the first call.
% trace: experiments/exp010_flagship/README.md (pre-registration); results/plan.json

\paragraph{Statistical protocol.} All comparisons are paired per problem. For a contrast
between cells we take each problem's majority outcome over the five runs and apply the exact
McNemar test to the discordant pairs; we additionally require the mean per-run difference to
exceed the minimum effect sizes of Sec.~\ref{sec:protocol}. We call this pair of
requirements (minimum effect size \emph{and} $p<.05$) the \emph{decision bar}; a
difference that clears only one of the two is reported as within noise. Cells are reported
as per-run totals, never as single runs. Null results are reported as results.

\paragraph{Telemetry.} Every LLM call is logged with token counts, cost, and a
problem/cell/run tag. This telemetry is what makes the mechanism analysis of
Sec.~\ref{sec:results-mech} possible, and it ships with the artifact.
Table~\ref{tab:config} lists the configuration held fixed across all cells.

\paragraph{Threats owned by design.} HumanEval is the field's most familiar benchmark and
predates every current model's training data, so we treat it as within-distribution; the
LiveCodeBench window is the off-distribution check, its problems post-dating the weak
model's training data by over a year. No benchmark identifier reaches any model: we verified
across all $7{,}962$ logged prompts of the two experiments that rendered prompts carry the
problem statement and its worked examples only, never a problem number or benchmark name a
memorizing model could key on. The frontier model's training cutoff is not public;
Sec.~\ref{sec:threats} argues the design is robust in the direction that matters. Both problem
sets are chosen for measurability (hardness-enriched; weak-model band), so per-run counts are
not benchmark rates and are never reported as such.

\subsection{RQ1: the gap on the corrected instrument}
\label{sec:results-gap}

Table~\ref{tab:cells} carries the complete result matrix; Figure~\ref{fig:asym} plots the
error decomposition. On the all-weak control the gap is present on both benchmarks and
two-sided. Per 30-problem run, HumanEval: $24.0$ oracle passes, $4.0$ false accepts against

oracle, post-cutoff problems): $15.2$ oracle passes, $4.8$ false accepts ($29\%$ of claims),

these problems, and the private tests never enter any prompt. Every false accept is, by
construction, a self-consistent misalignment, tests and code agreeing with each other against
the specification. Every false reject is correct code the pipeline paid to produce and then
abandoned on its own tests' veto.

\subsection{RQ2: frontier models in the verification roles}
\label{sec:results-asym}

\paragraph{The false-success rate does not change anywhere.} Eight cells, two benchmarks,
three ways of inserting a frontier model into verification: no false-accept contrast clears
the decision bar. On HumanEval the counts do not even move directionally with the judge
($4.0 \to 3.2/4.4/3.4$, all $p{=}1.0$; the frontier-judge cell sits \emph{above} control);
on LiveCodeBench they lean down ($4.8 \to 2.8/2.4/3.0$) but no contrast is significant
($p \in [0.125, 0.375]$), and we report the direction: at $N{=}5$ an effect this
size cannot be distinguished from run noise. This was the pre-registered confirmatory
prediction (H-B2), and it held: the probability that a claimed success is wrong stays
material, $2.4$--$4.4$ per run, whoever grades. The residual false accepts are not
weak-model sloppiness that a stronger verifier would catch; they are the structural blind spot
built into the loop.
% trace: exp006 ANALYSIS.md contrasts; exp007 ANALYSIS.md contrasts (FA rows)

\paragraph{The null survives two more frontier verifiers.} A skeptic can grant the null for one
just-released model of unpublished verification skill and still suspect it of that model in
particular. We pre-registered and reran the entire asymmetry design with two more frontier
verifiers, chosen for the opposite property: Gemini-2.5-Pro, the top-ranked code judge on an
execution-grounded judge benchmark~\cite{jiang2025codejudgebench}, and Claude-4.5-Sonnet, the current
release of the second-ranked Sonnet line. Holding the weak generator fixed and swapping only the
strong role, across both benchmarks and all twelve strong cells not one false-accept contrast clears
the decision bar (Table~\ref{tab:verifiers}, Figure~\ref{fig:verifiers}): two of the strongest
reported code judges leave the false-success rate where the weak model left it, while false rejects
again fall under the strong judge (both LiveCodeBench judge cells and both HumanEval judge cells
reduce them). The soundness null now persists across all three frontier verifiers we test---GPT-5.6
Terra, Gemini-2.5-Pro, and Claude-4.5-Sonnet, spanning OpenAI, Anthropic, and Google, and unknown,
first-, and second-ranked judging pedigree. We claim this for the verifiers and benchmarks we
measure, not for models at large.

\subsection{RQ3: the improvement flows through feedback}
\label{sec:results-mech}

The pipeline's telemetry locates the mechanism. Canonical (anchored) tests are constant at
$75$ per run in every LCB cell; the anchoring mandate saturates. What changes is the volume
the judge demands beyond them: control suites hold $\sim76$ tests per run; the frontier
judge's \texttt{ADD:} directives push suites to $182$–$194$, and cycle completions rise from
$\sim17/30$ to $23$–$24/30$ while completed cycles stay correct at a comparable rate. The
judge's influence flows through the retry loop's feedback channel, with richer tests steering
the weak generator toward correct implementations, and not through its accept verdicts, whose
error rate (the false accepts) never clears the bar in any cell. The strong test author writes
larger suites too ($140$ per run), but \emph{once}, with no iterative pressure on the
generator: the pass rate does not move, and only the composite verdict error improves.

\subsection{RQ4: the gap widens at application scale}
\label{sec:results-scale}

On RGRBench the gap is not a small-problem artifact; it is larger. In the control cell $65$
of $261$ valid runs end in a self-claimed success, and $41.5\%$ of those claims fail the
hand-verified oracle ($95\%$ Wilson CI $[30.4, 53.7]$); the strong-judge cell claims $50$
successes over $251$ valid runs at a statistically indistinguishable $42.0\%$
($[29.4, 55.8]$). This is roughly double the $18\%$/$29\%$ of the algorithmic benchmarks, and
even the lower confidence bound ($30\%$) exceeds their point estimates.
Figure~\ref{fig:misalignment} makes one of these false accepts concrete on a fully specified
package. RGRBench grades a

the adapter's contribution to these numbers directly; an automated calibration puts it at
$0.000$ (Sec.~\ref{sec:threats}). Three pre-registered properties sharpen the picture
(Table~\ref{tab:scale}).

\section{Discussion}
\label{sec:discussion}

\paragraph{Completeness improves; soundness does not.} The two error directions respond to
verifier strength in opposite ways, and the split is principled. False rejects are failures the loop
can \emph{see}: a test fails, the cycle retries, feedback accumulates. A stronger judge
converts that visibility into repair, and on unseen problems it eliminates the error class
outright, zero false rejects in ten of ten frontier-judge runs. False accepts are failures the
loop \emph{cannot represent}: tests and code agree, every internal signal is green, and there
is no residual for any judge, however capable, to inspect. The judge grades the tests against
its reading of the specification; when the test author's misreading is a plausible one, the
judge makes that reading \emph{more} internally consistent. It does not check the reading
against what the specification means. Model strength added inside the loop improves completeness
because completeness failures are visible inside the loop; it cannot improve soundness because
soundness failures, by construction, are not.

\paragraph{The judge is a coach, not a gatekeeper.} The largest effect in either matrix, the
five-to-six-problem pass-rate lift on unseen problems, is not a verification effect at all. It
is the frontier judge \emph{teaching} the weak pipeline through demanded tests and directive
feedback, visible in the tripled suite sizes and the recovered cycle completions. This
reframes the production intuition that motivated the experiments: asymmetric deployments
(cheap generator, frontier model in the loop) are valuable, and our data says the
value concentrates in the judge seat rather than the test-author seat. But the mechanism is
generation quality rather than verdict quality. The verdicts that matter for trust, ``this is
correct, ship it,'' are exactly as unreliable as before.

\paragraph{Implication for builders.} A self-testing pipeline's accept verdict is not
evidence of correctness at any verifier strength the loop can buy, and the improvement that
model strength \emph{does} deliver makes the verdicts more numerous (more cycles complete)
without making them sounder: a pipeline that completes more and self-accepts at the same
false-accept rate ships \emph{more} wrong code, more confidently. The calibration channel
has to come from outside the loop: held-out test suites, differential testing against
independent implementations, or accounting of verdict-versus-outcome on problems with known
answers. No component inside the loop can supply that calibration.

\paragraph{Why the strong test author disappoints.} The null on frontier-authored tests is
the study's most counterintuitive cell. One reading: test quality binds through iteration,
not authorship. A suite written once, however competently, exerts no corrective pressure on
a weak generator's misreadings, while an adversarial reviewer of the weak model's own suites
forces the specification to be re-derived every retry. This is exploratory interpretation;
the pre-registered fact is the null.

\paragraph{The gap is a validation failure, born at comprehension.} Every intervention we test
lives downstream of the moment a natural-language specification becomes a test suite, and none
moves the false-accept rate, because the misalignment is fixed at that moment, not after it.
In the vocabulary of requirements engineering the loop performs \emph{verification} flawlessly
(the code is built right, to its tests) while never performing \emph{validation} (the tests
are the right ones, faithful to the intent)~\cite{boehm1984vv}. Read this way the
soundness-invariance result is less a surprise than a near-tautology: no amount of verification
strength closes a validation gap, because the two answer different questions. The failure long
predates LLMs. It is the requirements ``telephone game'' in which a specification, refracted
through each reader's domain assumptions, yields systems built correctly to the wrong intent;
waterfall took months or years to surface such errors, and agile shortened the loop only where
an external oracle (a customer, a failing production case) could expose the misread. A
self-testing agent removes that oracle and re-runs the same misunderstanding at inference
speed. The pattern holds even when the input is pre-structured. On RGRBench the pipeline is
handed a user-story requirements document with explicit acceptance criteria, not a bare
prompt, and the false-accept rate is still $42\%$ (Figure~\ref{fig:misalignment} traces one such
false accept end to end). Structure at the story level does not
remove the interpretive freedom of the natural-language-to-test step where the gap is born.

\paragraph{Attacking the initial conditions.} If the gap is set at comprehension, the lever our
experiments never touch is the \emph{input} to test authoring. Decomposing and disambiguating a
specification into refined stories and acceptance criteria precise enough to read as pseudo-code
for the tests would narrow the interpretive distance the RED author must cross, lowering the
gap's initial magnitude instead of trying to catch it afterward, which is what our strong-judge
and strong-author cells attempt without success. We did not test this, and one caution follows
directly from the reframing above: a refinement stage that generates its own acceptance criteria
self-consistently merely relocates the comprehension step, it does not remove it. Such a
front-end most plausibly helps when the refined criteria are validated against intent from
outside the loop: a human sign-off on the acceptance criteria, in the spirit of TiCoder's
interactive test validation~\cite{fakhoury2024ticoder} lifted to the requirements layer.
Building and measuring such a front-end on RGRBench is the constructive next step this diagnosis
points to.

\section{Threats to Validity}
\label{sec:threats}

\paragraph{Construct.} The gap is defined relative to an oracle; a weak oracle understates it
and any oracle's own defects transfer. We measure against three oracles of increasing
distance (visible-adjacent, strong, hidden) and the phenomenon persists under all three.
Self-verdicts are harness-captured execution outcomes, not model claims. On RGRBench two
further defenses apply. The oracle's own blind spots are bounded rather than assumed (mutation
kill rate $0.981$, every surviving mutant individually classified), so the held-out suite's
error is a measured quantity. And because RGRBench grades through a generated adapter, a
mis-mapping adapter could in principle inflate false accepts; an automated calibration
mangles each package's known-correct reference solution to an opaque foreign API (a
behavior-preserving AST transform) and regrades it through a blind, model-authored adapter, so
any resulting failure is pure adapter error. Behavior-preservation is certified per package
before it counts, and the measured adapter-attributable false-accept rate is $0.000$ across
all tiers (13 usable packages, the hardest included). The application-scale gap is not a
plumbing artifact.
% trace: experiments/exp010_flagship/calibrate_adapter.py, calibration/calibration.json;
% trace: rgrbench instrument/mutation_scores.json, equivalent_mutants.md

\paragraph{Internal.} We study one pipeline. Its complete instrument (engine, prompts,
and the defect register from a line-by-line review of the pipeline) ships with the artifact, and
every reported number comes from that instrument.

\paragraph{External.} Three benchmarks and three frontier verifiers now: two single-function
algorithmic benchmarks and RGRBench's $89$ multi-concern packages, with the strong role filled in
turn by GPT-5.6 Terra, Gemini-2.5-Pro, and Claude-4.5-Sonnet across three providers
(Table~\ref{tab:verifiers}). Two designated robustness checks, both pre-registered: the move to
application-scale, test-first-built corpora with hand-verified oracles strengthened rather than
softened the finding (Sec.~\ref{sec:results-scale}), and the verifier replication reproduced the
soundness null on every benchmark. What remains is generator diversity---the generator is held at
one weak model \emph{by design}, to isolate the verifier's effect---and a public leaderboard over
many generator/verifier systems on RGRBench, left as released-benchmark future work. The verifiers'
training cutoffs vary, and some exposure to the LCB window is possible for the later two; the design
is robust in the direction that matters, since judge-side memorization of solutions could only
\emph{reduce} false accepts, and across all three verifiers they did not move. The pass-rate lift, however, could in principle be flattered by exposure;
its mechanism (test volume, feedback, completions) is measured, not assumed. One pipeline is
studied; the protocol is portable, the constants are not.

\paragraph{Conclusion validity.} Per-problem outcomes are unstable across identical runs; we
pre-registered practical floors alongside significance tests, confirmed the floors
conservative against observed control spreads, and treat sub-threshold differences as noise
regardless of $p$-value. $N{=}5$ runs per cell bounds power: effects smaller than the floors
would not be detected, which is why the invariance claim is stated as ``within pre-registered
noise,'' not as a proof of zero effect.

\paragraph{Execution safety.} The pipeline runs model-generated tests and code as ordinary
subprocesses, each in an ephemeral per-run working directory with a pinned interpreter and
\texttt{PYTHONPATH} scoped to that directory, under wall-clock timeouts ($30$\,s per test run,
$120$\,s per oracle run). This bounds runaway execution but is not a hardened sandbox: there is
no container, no memory or CPU limit, and no network isolation. Running untrusted model output
at larger scale should add OS-level isolation.

\paragraph{Anchoring.} The RED prompts anchor one test per canonical example
(App.~\ref{app:prompts}); we ablated this across four variants (both sides, generator-only,
judge-only, neither) on three generator models, committed in the artifact. Across variants the
aggregate pass and self-verdict rates move only marginally. The case studies of
App.~\ref{app:cases} show why anchoring cannot close the gap: it makes the specification's
worked examples covered, but example coverage is not specification coverage, and every false
accept we inspected passes the anchored examples and fails only on inputs beyond them. A
false-accept-instrumented anchoring ablation across models is left as released-benchmark future
work.

\section{Conclusion}
\label{sec:conclusion}

A pipeline that writes its own tests holds its own report card, and nothing in the loop is
tasked with grading the grader. We defined the verification gap to make that missing function
measurable, measured it on three benchmarks (one whose problems the generator had never
seen and whose tests no prompt ever contained, and one built at application scale with
hand-verified, error-barred oracles), then paid for the obvious remedy: a frontier model in
the verification roles. The report card is wrong about roughly one claimed success in four,
and it stays wrong under a frontier test author, a frontier judge, and both at once---and under
all three frontier verifiers we tried, across three providers. What the
frontier judge buys is worth buying: false rejects vanish, and on unseen problems its
feedback lifts true pass rates by a third. But it is a better coach, not a better gatekeeper,
and every gain arrives through the feedback channel while the accept verdicts stay blind.
Verification strength inside a self-testing loop purchases completeness, never soundness. And
the blind spot is not a small-problem curiosity. On RGRBench's application-scale, multi-concern
packages the report card is wrong about two claims in five, worse where the tasks are harder
and worse again after the loop's own retries: the same failure, larger where the programs look
more like the ones agents ship. For builders the implication is architectural. The accept
verdict of a self-testing agent is not evidence at any internal verifier strength, and
calibration must come from outside the loop: held-out oracles, differential checks, verdict
accounting, or, upstream, a requirement grounded in intent before it is ever encoded as a
test, since the gap is born in that translation and not in the grading that follows. No
assignment of models to the roles inside the loop removes it.

\section{False-accept case studies}
\label{app:cases}

Every false accept has the same shape: the self-authored suite pins the specification's worked
examples (the anchoring block of App.~\ref{app:prompts} forces one
\texttt{test\_canonical\_example} per example), the implementation passes them, and both miss a
behaviour the held-out oracle exercises. Three HumanEval false accepts make the shape
concrete---two from the all-weak control and one from the cell with a frontier judge, each
accepted with a top GREEN-judge score. Code and tests are verbatim from the committed run logs.

\paragraph{HumanEval/32 (\texttt{find\_zero}, control cell).} The spec asks for a root of an
arbitrary even-degree polynomial. The self-suite tests only the two docstring examples
(\texttt{find\_zero([1,2])} $\rightarrow -0.5$, \texttt{find\_zero([-6,11,-6,1])} $\rightarrow
1.0$). The implementation runs Newton's method from a fixed start \texttt{x=0.0} for $100$
iterations. Newton-from-zero converges on both example polynomials, so the suite passes, but it
is not a general root-finder: where the iteration stalls (\texttt{dfx==0}, and it breaks) or
diverges it returns a non-root. HumanEval\texttt{+}'s additional polynomials trigger exactly
that, and the oracle rejects. The tests certify the two points the code was shaped around, not
the specification.

\paragraph{HumanEval/74 (\texttt{total\_match}, control cell).} The spec returns the list with
the smaller total character count, \emph{and returns the first list when the totals are equal}.
The implementation gets the tie wrong: \texttt{if total1 < total2: return lst1} else
\texttt{return lst2}, so equal totals fall through to \texttt{lst2}. None of the five generated
example tests has a distinguishable tie---the only equal-total case is \texttt{([],[])}, where
both answers are \texttt{[]}---so the tie branch is never exercised. HumanEval\texttt{+} includes
an equal-total pair with different contents; the code returns the second list where the spec
demands the first, and the oracle rejects.

\paragraph{HumanEval/153 (\texttt{Strongest\_Extension}, frontier-judge cell).} Strength is
(uppercase count) minus (lowercase count); the strongest extension wins, ties to the earliest.
The implementation seeds the running maximum at \texttt{0} and updates only on \texttt{strength >
strongest\_strength}, so when every extension has non-positive strength and the strongest is not
the first, the loop never updates and it returns \texttt{extensions[0]}. The two generated tests
do not reach this state---example~1 is all-negative but its first element is already the
strongest, masking the bug---so the suite passes, and the frontier judge scored it $1.0$.
HumanEval\texttt{+} supplies an all-negative case whose maximum is not first, and the oracle
rejects.

\paragraph{At application scale.} The same signature recurs on RGRBench. The
\texttt{strong\_judge} run on \texttt{numbers\_to\_words} self-certifies, yet the held-out oracle
passes only $20$ of its $22$ tests; App.~\ref{app:telephone} reproduces this false accept in
full. The per-package artifacts (self-authored tests, generated package, and oracle outcome) are
committed for all $534$ runs.

\section{An RGRBench false accept in full: \texttt{numbers\_to\_words}}
\label{app:telephone}

The false accept of Figure~\ref{fig:misalignment}, laid out end to end. The pipeline sees only
the requirements below; from them it authors its tests and its implementation, and reports success
once the implementation passes those tests. The held-out oracle is applied afterward and never
enters the loop. The implementation is correct on every spelling rule; the single defect is the
exception \emph{type} on the range check---which the requirement leaves implicit (it fixes the
message, not the type), the pipeline's own test does not pin down (it accepts any
\texttt{Exception}), and the oracle does (it demands \texttt{ValueError}).

\paragraph{Requirements given to the pipeline.} User-story narratives are elided; the acceptance
criteria are verbatim.
\begin{small}
\begin{verbatim}
# Spelling numbers as English words

## Overview
A number-spelling service turns any whole number from 0 through
9999 into its English words, following everyday conventions:
hyphenated compounds for twenty-one through ninety-nine, no "and"
between parts, and plain spaces between the thousands, hundreds,
and remainder portions.

### US-1: Spelling numbers up to twenty
- AC-1.1: Zero is spelled "zero", and single digits use their
  names, such as "five" and "eight".
- AC-1.2: Ten is spelled "ten", and the teens are single
  unhyphenated words, such as "thirteen" and "nineteen".

### US-2: Spelling two-digit numbers
- AC-2.1: Round tens are single words with no hyphen, such as
  "twenty" and "ninety".
- AC-2.2: Other two-digit numbers are hyphenated tens-units
  compounds: 21 is "twenty-one", 77 is "seventy-seven", and 99
  is "ninety-nine".

### US-3: Spelling hundreds
- AC-3.1: 100 is "one hundred"; the leading "one" is always kept.
- AC-3.2: A hundreds part is followed by the spelled remainder
  separated by a space: 303 is "three hundred three", 555 is
  "five hundred fifty-five", and 115 is "one hundred fifteen".
- AC-3.3: The word "and" never joins the hundreds to the
  remainder.

### US-4: Spelling thousands
- AC-4.1: 1000 is "one thousand" with the leading "one" kept,
  and round thousands follow the same pattern, such as "two
  thousand".
- AC-4.2: The thousands part is followed by the spelled
  remainder: 2400 is "two thousand four hundred", 3466 is "three
  thousand four hundred sixty-six", and an empty hundreds part is
  simply omitted, so 5005 is "five thousand five".
- AC-4.3: The largest supported number, 9999, is "nine thousand
  nine hundred ninety-nine".

### US-5: Rejecting numbers outside the range
- AC-5.1: Negative numbers are rejected with an error whose
  message includes "must be in 0..9999".
- AC-5.2: Numbers greater than 9999 are rejected with the same
  error message wording.
\end{verbatim}
\end{small}

def test_reject_negative_numbers():
