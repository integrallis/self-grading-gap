\begin{abstract}
When a coding agent writes both code and tests, the two can agree while sharing the same
mistake. Passing those tests may then conceal a misunderstood requirement. We measure how
often code reported as successful fails tests that were not provided to the agent. We call this
mismatch the \emph{verification gap}.

We evaluate one test-first pipeline on selected HumanEval and LiveCodeBench problems and on
RGRBench, a collection of $89$ Python packages. With one inexpensive model writing tests,
generating code, and reviewing both, the withheld tests reject $\AuditHEControlGap\%$ of
claimed successes on HumanEval, $\AuditLCBControlGap\%$ on LiveCodeBench, and $41.5\%$ on
RGRBench.

We then test stronger models as test authors and reviewers while keeping the code generator
fixed. Across three providers on the single-function benchmarks, some settings produce fewer
success claims that fail the withheld tests, but the evidence for a reduction remains inconclusive.
In our main LiveCodeBench experiment, a stronger reviewer also helps the pipeline produce
more solutions that pass the withheld tests. On RGRBench, the same reviewer stops many tasks
before code is written and produces fewer passing solutions. Failures remain among claimed
successes in every configuration studied.

The practical lesson is to measure both what an agent produces and how reliably it judges
its own work. That judgment also depends on a clear task: some benchmark failures reflect
requirements that omit details demanded by the tests. We release the pipeline, recorded
runs, and analysis tools to support independent checks of coding agents' success claims.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Test-Driven Development (TDD)~\cite{beck2002tdd} uses a Red--Green--Refactor loop:
write a failing test for a requirement, implement behavior that passes it, then improve the
implementation while preserving the tests. Its usefulness depends on the tests representing
the intended behavior. Passing an executable contract cannot establish that the contract
itself captures the requirement.

Agent pipelines now run that loop independently, writing their own acceptance criteria. An LLM
takes a natural-language specification and turns it into a test suite, a second generation writes
code to pass those tests, LLM-as-a-judge reviewers check each step, and the pipeline declares
success when its code passes its tests. The pipeline comes with its own evidence.

But TDD can still fall victim to misunderstandings of the requirements. Those misinterpretations
are now locked into code that drives the pipeline. What is the value of passing tests if they are
checking the wrong thing? TDD practitioners already have a term for tests that mirror the code
instead of the requirement: the \emph{ugly mirror}~\cite{rudolph2008uglymirror}.

We will show that autonomous test-first pipelines create the conditions for the ugly mirror at
the stage where natural language is turned into tests. We call the resulting mismatch the
\emph{verification gap}: problems that a pipeline claims to have solved but that fail when checked
by an oracle the pipeline never sees (Sec.~\ref{sec:gap}).

This paper measures that gap by stress-testing an agentic test-first pipeline. In the control
setup, using a low-cost, non-frontier model in every role (hereafter \emph{all-weak}), the gap is
persistent and appears on both sides. Out of 30 problems per run, an average of $4.0$ reported
successes fail HumanEval's strong oracle ($\AuditHEControlGap\%$ of what the pipeline claims) and $4.8$ fail the
hidden oracle of a LiveCodeBench window that post-dates the generator's training cutoff ($29\%$ of
claims), while $\AuditHEControlFR$ and $3.4$ oracle-passing implementations per run are rejected
by the pipeline's tests or internal gates.
% trace: experiments/exp006_model_asymmetry/results/ANALYSIS.md (control_rerun)
% trace: experiments/exp007_lcb_asymmetry/results/ANALYSIS.md (control)

The most common fix for a model that misunderstands a requirement is to use a stronger model
to write the tests. LLM-as-a-judge is also widely used to review the generated code at every
stage. Production systems are increasingly using this asymmetric approach: a cheap model generates,
and a frontier model is used somewhere in the verification roles. The \emph{test author} turns the
specification into a test suite, and the \emph{judge} reviews the tests and code and examines the
failures. We test these approaches as well: we place a frontier model in the test-author role, the
judge role, and both, while keeping a fixed weak generator (gpt-4o-mini) on both benchmarks. We
then repeat the design across three frontier verifiers and three providers (GPT-5.6 Terra,
Gemini-2.5-Pro, Claude-4.5-Sonnet; Sec.~\ref{sec:design}). The primary experiment suggests an
asymmetry: the frontier judge improves oracle success on LiveCodeBench, while residual false
accepts remain in all conditions. No false-accept contrast passes the specified decision bar,
but this is a failure to establish a reduction, not evidence that verifier strength cannot
help. Some false-accept point estimates decrease substantially. Counts must also be separated
from the error rate among accepted outputs because the interventions change acceptance and
whether the pipeline produces code at all.

\paragraph{From algorithm to application scale.} Both HumanEval and LiveCodeBench above were
designed as single-function, mostly algorithmic problems and do not represent software applications
that have stateful behavior, multiple files, classes, or components, and complex collaboration
patterns between them. To examine the gap on larger tasks, we
built RGRBench: $89$ Python packages spanning small kata and larger stateful, multi-concern
examples (event sourcing, reservations, billing) across three difficulty levels, each with a hand-reviewed suite assessed
using mutation testing (mutation kill rate $0.981$, with surviving mutants classified). This
set of applications was created in a TDD style by translating and curating TDD examples from other
programming languages when no Python version was available.

Our pipeline receives each package's extracted requirements, with benchmark code and tests
withheld. Across the $534$ planned runs, the control's conditional gap is $41.5\%$ and the
strong judge's is $42.0\%$. Higher observed gap rates accompany harder packages and additional
GREEN attempts. These comparisons do not isolate causal effects of complexity or retries.
The stronger judge also blocks many more packages before code generation, reducing total
correct output. RGRBench extends the measurement to larger tasks while exposing selection
and oracle-fidelity limitations that must accompany its headline rate.

\section{Background and Related Work}
\label{sec:related}

\paragraph{Weak tests overestimate, in benchmarks and pipelines alike.}
EvalPlus showed that the tests in the benchmark were the weak point in code
evaluation: by expanding HumanEval's test suites, it found a significant amount of previously
unnoticed incorrect code and changed the order of model rankings~\cite{liu2023evalplus}.
LiveCodeBench addressed the related issue of contamination by using a rolling problem collection
approach~\cite{jain2024livecodebench}. We used both tools. EvalPlus serves as a strengthened
oracle, and for LiveCodeBench, we rely on a post-cutoff window as a hidden oracle. In the TDD
pipeline, when the tests are weak, this overestimation happens inside the loop, and the
pipeline's own self-assessment shows the same lack of awareness that EvalPlus found in
benchmarks. At repository scale, Ahmed et al. compare generated-test-passing patches with
held-out golden tests~\cite{ahmed2025overfitting}, while SWE-ABS re-evaluates
benchmark-passing patches with strengthened suites~\cite{yu2026sweabs}. What we
call the verification gap is the TDD-internal, agent-native version of this phenomenon, measured
with additional mutation and adapter checks on RGRBench. These checks characterize the
instrument; they do not estimate its population error rate. The cited SWE-bench studies use
different acceptance events and denominators, so their rates are contextual comparisons.

\paragraph{The ugly mirror.}
TDD practitioners have long described the failure that happens when tests are written
after the implementation already exists: the \emph{ugly mirror}~\cite{rudolph2008uglymirror},
where a test simply reflects the code and confirms what it does, rather than what it should do,
with the tautological test as the extreme case~\cite{pereira2010ttdd}. Writing tests before the
code removes direct dependence on an existing implementation, but cannot prevent
misunderstanding the specification. Our subject pipelines use this order, and yet we see
that the mirror effect still appears, just at a higher level. When a model writes tests based on its
interpretation of the specification and a similar model writes code to pass those tests, both the
tests and the code can reflect the same misunderstanding, and successful test execution then
establishes agreement on the generated cases. The pipeline then reports this internal consistency
as success, but it only shows that the tests and the code are in agreement.

\paragraph{Test-first generation with LLMs.}
Providing tests with problem statements improves generation~\cite{mathews2024tdd}; TiCoder
makes the authorship of tests more interactive---a human checks the proposed tests before the
code is accepted~\cite{fakhoury2024ticoder}; TENET and TDFlow extend test-driven loops to
repository-scale agents~\cite{sun2025tenet,tdflow2025}. Testing is provided, verified by humans,
or evaluated end-to-end by the impact on pass rates. Our subject class is the fully autonomous
case, in which the pipeline authors both tests and code. What we are interested in is the
reliability of the pipeline's own verdict on itself. End-to-end pass rates alone do not reveal whether a pipeline's internal acceptance
correctly distinguishes the outputs that will pass the held-out oracle.

\paragraph{Self-generated tests as a signal.}
CodeT uses generated tests to rank candidate solutions through execution
agreement~\cite{chen2023codet}. ConVerTest combines self-consistency, code verification, and
execution agreement, evaluating test validity and coverage~\cite{convertest2026}. Such
signals can improve selection without guaranteeing correctness. Our study measures residual
oracle disagreement in a different, test-first pipeline; it does not reproduce or refute
those methods' reported improvements.

\paragraph{LLM judges on code.}
Benchmarks evaluating LLMs as judges for coding tasks show that these judges are imperfectly
aligned with execution results, with performance varying by model and task~\cite{jiang2025codejudgebench}, and that LLMs
consistently struggle when checking code against natural-language
specifications~\cite{verifyfailures2025}. In our subject pipeline, we include judges as
checkpoints in the process, along with an execution gate that can override the judge's
predictions. The asymmetry experiments extend these findings: upgrading the judge to a frontier
model is associated with higher oracle success in the primary LiveCodeBench experiment,
consistent with useful feedback, while some accepted outputs still fail the oracle.
Because changing the judge also changes generation, this experiment does not isolate its
classification accuracy on a fixed set of implementations.

\paragraph{Multi-agent code generation.}
Multi-agent SDLC frameworks have been effective at handling end-to-end
tasks~\cite{hong2024metagpt}. End-to-end performance is complementary to auditing internal acceptance gates. Our protocol offers a
complementary and transferable approach: any pipeline with a harness that records its executed
self-verdict and outputs can use the same measurement.

\paragraph{The oracle problem and imperfect verification.}
The difficulty of deciding whether software behaves correctly is the established oracle
problem in software testing~\cite{barr2015oracle}. Work on inference scaling analyzes
imperfect verifiers when selecting among repeated code-generation attempts~\cite{stroebl2026resampling}.
Our contribution is a measurement of this problem inside an executed test-first pipeline,
with role interventions and accounting of accepted and rejected outputs; the general
limitation of incomplete tests is not new.

\paragraph{Connection to context ablations.}
Sam-Bodden~\cite{sambodden2026context} studies what code representation a coding agent needs
after localization is fixed, using independent SWE-bench outcomes and repeated API runs.
That study motivates the same separation between an agent's intermediate representation and
external evidence of task success. Here the intermediate artifact is a self-authored test
suite. The benchmarks, interventions, and outcome definitions differ, so the context study
is complementary methodological work rather than a replication of the verification gap.

\label{sec:gap}

\subsection{Definitions}

Consider a code-generation pipeline that, for a problem $i$ with natural-language
specification $\mathit{spec}_i$, produces an implementation $y_i$, a test suite $T_i$ that the
pipeline itself wrote from $\mathit{spec}_i$, and a self-verdict
$s_i \in \{0,1\}$, the pipeline's own claim that the problem is solved, based on running
$T_i$ against $y_i$ and from any internal quality gates (in our subject pipeline, LLM judges).
An \emph{oracle verdict} $o_i \in \{0,1\}$ is the outcome of a test suite the pipeline never
sees. We use three oracles of increasing distance from the pipeline's inputs: the
\emph{visible-adjacent oracle} $o^{\mathrm{base}}_i$ (HumanEval's original tests, which
overlap the worked examples visible in $\mathit{spec}_i$), a \emph{strong oracle}
$o^{\mathrm{plus}}_i$ (HumanEval\texttt{+}~\cite{liu2023evalplus}, whose tests go far beyond
the visible examples, by roughly two orders of magnitude), and a \emph{hidden oracle}
(LiveCodeBench's private test sets~\cite{jain2024livecodebench}, never distributed with the
problem statement at all).

The \emph{verification gap} of a run over problems $P$ is the set
$G = \{\, i \in P : s_i = 1 \wedge o_i = 0 \,\}$: problems the pipeline believes it solved and
the oracle rejects, the \emph{false accepts}. We report it as a per-run count over $|P|$ and,
where the denominator matters, as the \emph{conditional gap} $|G| / |\{ i : s_i = 1 \}|$, the
observed fraction of claims rejected by the chosen oracle. The complementary error set
$R = \{\, i : s_i = 0 \wedge o_i = 1 \,\}$ (\emph{false rejects}: oracle-passing code rejected by the
pipeline's tests or internal gates) completes the picture; self-verification error runs in both directions
(Table~\ref{tab:confusion}).

Every element of $G$ is an observed disagreement: an accepted implementation passes the
pipeline's execution gate but fails an external suite. An incomplete self-suite, an incorrect
expected value, an implementation defect, an underspecified requirement, or an oracle or
adapter error can all produce this observation. The definition alone does not establish that
the implementation violates the visible specification or that tests and code share a
misunderstanding. We use \emph{self-consistent misalignment} for cases where inspection
supports that interpretation, and retain \emph{oracle-relative false accept} for the measured
event. HumanEval case studies illustrate missed specified behavior; the RGRBench example
in Appendix~\ref{app:telephone} instead exposes a requirements--oracle mismatch.

\subsection{Subject pipeline}

Our subject is a test-first multi-agent pipeline in which an LLM writes tests from the
specification (RED), an LLM judge scores the tests, a second generation step writes an
implementation against those tests (GREEN), a judge predicts test outcomes, an execution
gate then runs the tests and overrides optimistic judge predictions, and a final VERIFY phase
runs the full suite, with bounded retries and textual feedback loops
(Algorithm~\ref{alg:tdd}, Fig.~\ref{fig:loop}). The pipeline's main configuration also
\emph{anchors} self-authored tests: prompt and judge together require that every worked example
in the specification appear as a test case exactly as given. Note what the execution gate cannot do:
it checks $y$ against $T$, so a wrong $T$ passes it incorrectly.

The complete instrument (engine, prompt templates, and the defect register from a
line-by-line review of the pipeline) is included with the artifact.
% trace: src/vgap/pipeline/REVIEW.md (H-1..H-15, B-1..B-10, E-1)

\begin{algorithm}[t]
\caption{Execution-gated TDD cycle (subject pipeline; generator $G$ and judge $J$ are
role-assigned per experimental cell)}
\label{alg:tdd}
\begin{algorithmic}[1]
\Require spec, test author $G_T$, code generator $G$, judge $J$, threshold $\tau$, retries $R$
\State $f \gets \varnothing$
\For{$r \gets 1 \ldots R$} \Comment{RED: author the tests}
  \State $T \gets G_T.\mathrm{tests}(\mathrm{spec}, f)$;\quad $q \gets J.\mathrm{score}(T, \mathrm{spec})$;\quad $f \gets J.\mathrm{feedback}$
  \If{$q \geq \tau$} \textbf{break} \EndIf
\EndFor
\If{$q < \tau$} \Return $s{=}0$ \EndIf
\State $g \gets 0$
\For{$r \gets 1 \ldots R$} \Comment{GREEN: code against own tests}
  \State $y \gets G.\mathrm{code}(\mathrm{spec}, T, f)$;\quad $\hat{q} \gets J.\mathrm{predict}(y, T)$
  \If{$\hat{q} \geq \tau$}
    \If{$\mathrm{run}(T, y).\mathrm{allPass}$} $g \gets 1$; \textbf{break} \Comment{execution gate: judge overruled by pytest}
    \Else\ $f \gets \mathrm{debugAnalysis}(T, y)$ \EndIf
  \Else\ $f \gets J.\mathrm{feedback}$ \EndIf
\EndFor
\If{$g = 0$} \Return $s{=}0,\,y,\,T$ \EndIf
\For{$r \gets 1 \ldots R$} \Comment{VERIFY: full suite; failures route back to GREEN}
  \If{$\mathrm{run}(T, y).\mathrm{allPass}$} \Return $s{=}1,\, y,\, T$ \EndIf
  \State $f \gets J.\mathrm{analyzeFailures}(T, y)$;\quad regenerate $y$ as in GREEN
\EndFor
\State \Return $s{=}0,\, y,\, T$
\end{algorithmic}
\end{algorithm}

\subsection{Prompt architecture}
\label{sec:prompts}

Four prompts drive the loop; their structure is part of the instrument and matters to the
results, so we describe it. (Skeletons in Appendix~\ref{app:prompts}; the templates come with
the artifact under a SHA-256 manifest, with render-contract tests asserting the properties
below.)

\emph{RED generator.} Role framing (``your tests are the only specification the implementer
will see''), task description and full specification, scenario list, and finally an
\emph{anchoring block}: for every worked example in the specification, a test named
\texttt{test\_canonical\_example\_N} with the example's exact inputs and outputs and a one-line
derivation comment. There are five rules that must be followed: only test the specified behavior,
use exact signatures, compute expected values, import from the solution package, and use
plain pytest. On retries, the judge's directives and the previous attempt are included. The output
contract is a single fenced Python block.

\emph{RED judge.} The judge considers a single question: does the suite faithfully verify the
specification? This is done through a series of ordered checks: canonical-example coverage (an
anchoring block that mirrors the generator's; any missing or changed example results in the
minimum score), assertion fidelity (recalculate each expected value), no invented constraints,
coverage of all stated behaviors, and sanity. A deduction schedule links findings to a score; the
response always ends with the line \texttt{Final score: <x.xx>}, and feedback is given as
apply-verbatim \texttt{ADD:}/\texttt{REMOVE:}/\texttt{FIX:} directives, which is the feedback
channel examined in Sec.~\ref{sec:discussion}.

\emph{GREEN generator.} The tests are given as the acceptance criterion; the rules prohibit
hardcoding test inputs and inventing behavior; the output is a single JSON object containing the
implementation file (with path, action, and content). This is the only structured output where
code appears as an escaped string field.

\emph{GREEN judge.} Predicts per-test PASS/FAIL by tracing the implementation against each
test, flags test-gaming in one line and must end with \texttt{Rating: <x.xx>} (predicted pass
fraction). If the judge clears the threshold, the execution gate runs the tests, so a positive
judge prediction alone cannot produce an accepted output.

The anchoring blocks in the RED pair are delimited by markers in the template source, and the
ablation variants of the artifact (generator only, judge-side only, neither) are produced by
stripping those blocks automatically; the variant used in every run is checked on the rendered prompt
at smoke time. A fifth template, the failure analyst of the retry loops in Sec.~\ref{sec:gap},
is triggered when an execution gate or VERIFY run fails. It follows each failed test and identifies the
root cause and emits \texttt{FIX DIRECTIVES:} lines that the next GREEN attempt uses
verbatim; it presents analysis only, never code.

\subsection{Measurement protocol}
\label{sec:protocol}

Three requirements make the gap measurable rather than anecdotal (Algorithm~\ref{alg:audit}).

\begin{algorithm}[t]
\caption{Verification-gap measurement over instrumented runs}
\label{alg:audit}
\begin{algorithmic}[1]
\Require pipeline $P$, problems $\mathcal{P}$, held-out oracle suites $O$, runs $N$
\For{each problem $i \in \mathcal{P}$, run $r \in 1..N$}
  \State $(y_{ir}, T_{ir}, s_{ir}) \gets P(i)$ \Comment{harness captures artifacts + the executed self-verdict}
  \State $o_{ir} \gets \mathrm{Exec}(O_i \text{ on } y_{ir})$ \Comment{standard harness (EvalPlus / LCB / RGRBench adapter), outside the loop}
\EndFor
\State $G \gets \{ (i,r) : s_{ir}{=}1 \wedge o_{ir}{=}0 \}$;\quad $R \gets \{ (i,r) : s_{ir}{=}0 \wedge o_{ir}{=}1 \}$
\State \Return $G, R$, per-run provenance and cost
\end{algorithmic}
\end{algorithm}

\emph{(1) Both verdicts captured independently.} The self-verdict $s_{ir}$ is the pipeline
graph's recorded success flag. Acceptance requires successful final test execution; rejection
can instead arise at a judge gate or retry limit, including before an implementation exists.
It is not simply a binary result of executing the final self-suite. Runs retain per-call
token and cost accounting. The
oracle verdict is obtained on the produced implementation outside the loop by the benchmark's own
harness: EvalPlus~\cite{liu2023evalplus}, LiveCodeBench's evaluator~\cite{jain2024livecodebench}
for the hidden-test problems, and RGRBench's hand-verified suites through a non-cheating adapter
(Sec.~\ref{sec:results-scale}). Every number in this paper comes from these two recorded
streams, the self-verdict and the oracle, and can be rebuilt from committed per-run artifacts.
% trace: src/vgap/pipeline/humaneval_runner.py, lcb_runner_local.py;
% trace: experiments/exp007_lcb_asymmetry/score_lcb.py (harness-side scoring)

\emph{(2) Oracles beyond the visible examples.} Anchoring ties $T_i$ to the
specification's worked examples, which HumanEval's base oracle partially shares; a gap
measured only against $o^{\mathrm{base}}$ understates the phenomenon. On the all-weak
setup, false accepts average $3.0$ per 30-problem run against the base oracle and
$4.0$ against HumanEval\texttt{+}.
% trace: exp006 ANALYSIS.md (control_rerun fa_base/fa_plus)
The LiveCodeBench experiment removes visibility entirely: prompts include the statement and its
public examples, while scoring uses the private suites, on problems whose contest dates
are more than a year after the weak model's training cutoff.

\emph{(3) Repeated-run variability and practical thresholds.} Per-problem outcomes are unstable across
byte-identical runs: the all-weak setup disagrees with itself on $6/30$ problems (HumanEval
subset) and $9/30$ (LiveCodeBench) across five runs, with maximum pairwise pass-total
differences of $4$ and $3$.
% trace: exp006 scores/ per-run eval results; exp007 scores/ (flip counts derived in
% scripts/make_figures.py inputs; totals in each ANALYSIS.md)
The protocols specify minimum effect sizes ($4$ problems on
success-rate contrasts, $2$ on false accepts, $2$ on false rejects, $3$ on total verdict
error) alongside statistical significance. These practical thresholds are not confidence bounds
or equivalence margins; some control error-count spreads exceed them. The observed
variability cautions against treating small single-run differences as stable effects.

\section{Study Design}
\label{sec:design}

The study asks four questions.
\begin{description}
\item[\textbf{RQ1 (phenomenon).}] How large is the verification gap, against visible-adjacent,
strong, and hidden oracles, and how does it break down into false accepts and false rejects?
\item[\textbf{RQ2 (asymmetry).}] Does a frontier model in the verification roles (as test author,
as LLM-as-a-judge reviewer, or both) close the gap?
\item[\textbf{RQ3 (mechanism).}] When a stronger verifier does help, does the improvement come
from its \emph{verdicts} (better gatekeeping) or from its \emph{feedback} (better generation)?
\item[\textbf{RQ4 (scale).}] Do the size of the gap and its resistance to verifier strength persist
when moving from single-function algorithms to larger, application-scale programs that involve
multiple concerns, and how does this gap change with increasing task complexity or as the loop
itself is refined?
\end{description}

\paragraph{Experiments.} The model experiments use a single asymmetry design with four conditions
(\emph{cells}): a weak model W (\texttt{gpt-4o-mini}) generates code in every cell; a frontier
verifier S replaces W in the test-author role, the judge role (covering all three judge duties), or
both; the control condition uses W in every role. We assign the S role to three verifiers from
three different providers---GPT-5.6 Terra, Gemini-2.5-Pro, and Claude-4.5-Sonnet\footnote{\texttt{gpt-4o-mini} is
OpenAI's GPT-4o mini. The verifiers are OpenAI's \texttt{gpt-5.6-terra}, Google's \texttt{gemini-2.5-pro}
(via Vertex AI), and Anthropic's \texttt{claude-sonnet-4-5}. All models are called through a LiteLLM
shim.}---and run this design on both benchmarks for each verifier. $N{=}5$ runs per cell, $30$
problems per run, model identity is fixed within each assigned role, and judge threshold and retries are held
constant. The single-function runners can switch late generation attempts to a second client
for the same model at a different temperature. The protocols record advance hypotheses,
but the public release history was reconstructed: original chronology depends on private
commits (\texttt{PROVENANCE.md}). Exp011 documents collection and retention changes during
the runs; these limit a strictly confirmatory interpretation. The primary pair uses GPT-5.6 Terra: exp006 runs a HumanEval subset that
includes previously unstable problems, scored by both EvalPlus oracles, and exp007 repeats this
on contamination-controlled data---all $19$ easy plus the first $11$ medium LeetCode problems from
LiveCodeBench release~v6 with contest dates $\geq$~2025-01-01, chosen by a deterministic rule fixed
in advance after a pilot identified the weak model's measurable range, and scored by the private LCB
suites. The exp007 protocol records predictions of fewer false rejects and no detectable
false-accept contrast, following exp006. The exp011 replication then reruns
both benchmark designs with the two non-OpenAI verifiers, Gemini-2.5-Pro and Claude-4.5-Sonnet, to
test whether the soundness null depends on which frontier model is used (Sec.~\ref{sec:results-asym}).
% trace: experiments/exp006_model_asymmetry/README.md, exp007_lcb_asymmetry/README.md,
% exp011_verifier_generalization/PRE_REGISTRATION.md (pre-registrations);
% experiments/pilots/README.md (band-location pilot)

\paragraph{The application-scale experiment.} A third experiment (exp010) moves to
RGRBench's $89$ packages. The pipeline receives only each package's requirements document
(user-story acceptance criteria derived solely from the tests, with the tests themselves never
shown) and is graded by the hidden, hand-verified suite through a non-cheating adapter
(Sec.~\ref{sec:results-scale}). The design keeps the judge-role contrast: a \emph{control} cell (weak model in every role) versus a \emph{strong-judge}
cell (GPT-5.6 Terra in all judge duties), with $N{=}3$ runs per package per cell ($534$ runs). Since
RGRBench labels each package by difficulty tier and the harness records whether a claim was made on
the first try or only after retries, these runs describe associations with complexity (H-D4) and additional attempts (H-D2).
Neither difficulty tier nor retry count is randomized.
% trace: experiments/exp010_flagship/README.md (pre-registration); results/plan.json

\paragraph{Statistical protocol and reporting correction.} For oracle-pass and false-accept
contrasts in the single-function experiments, the original analyzers take each problem's
majority outcome over five runs and apply exact McNemar tests, alongside practical thresholds
on mean per-run differences. We call these combined requirements the \emph{decision bar}.
Majority outcomes and mean changes are different estimands. Failing this bar does not establish
absence of an effect. The original scripts omit paired tests for false rejects and total
verdict error, and do not apply the protocols' larger-control-spread adjustment; these are
analysis deviations. Reported $p$-values are nominal, without multiplicity correction.

The original HumanEval summaries combine base-oracle pass and false-reject counts with
HumanEval\texttt{+} false accepts. Table~\ref{tab:cells} corrects this to use
HumanEval\texttt{+} throughout, recomputed from retained scores. The original summaries
remain available. A separately labeled post hoc audit provides complete matrices for both
oracles, the missing paired tests, and problem/package-cluster bootstrap intervals that
retain repeated runs together (\texttt{experiments/review\_audit/}). These supplemental
analyses do not retroactively become pre-registered confirmations.

\paragraph{Telemetry.} Retained successful LLM calls are logged with token counts, cost, and a problem, cell,
or run tag. This telemetry enables the mechanism analysis described in
Sec.~\ref{sec:results-mech}, and it is included with the artifact. Table~\ref{tab:config} lists the
configuration that remains fixed across all cells.

\paragraph{Threats addressed by design.} HumanEval is the field's best-known benchmark and
predates the training data of all current models, so we consider it within-distribution. The
LiveCodeBench window serves as the off-distribution check, since its problems were released more
than a year after the weak model's training data. In the audited primary runs, we checked all $7{,}962$ logged prompts from both experiments and confirmed that rendered
benchmark identity is conveyed through the statement and worked examples, without a
benchmark-name or problem-number label; generated tests, code, and feedback also appear in prompts. A date after the generator's reported cutoff reduces contamination concerns but does not
prove absence of exposure, particularly for later verifiers (Sec.~\ref{sec:threats}). Both problem sets are selected for measurability (with increased hardness; within the
weak-model band), so per-run counts do not represent benchmark rates and are never reported as
such.

\subsection{RQ3: telemetry is consistent with a feedback benefit}
\label{sec:results-mech}

Canonical tests average $75$ per run in the LCB cells. Total test volume changes from about
$76$ in control to $182$--$194$ in the frontier-judge cells, while cycle completions rise from
about $17/30$ to $23$--$24/30$. A frontier test author also produces larger suites ($140$

% trace: exp007 results/ANALYSIS.md; retained launch logs

These observations are consistent with stronger feedback helping generation. They do not
identify feedback as the cause: the judge intervention jointly changes scores, directives,
retry paths, test volume, and the selected outputs. The strong-test-author condition also
retains iterative review, so it is not a one-shot comparator. A feedback-only versus
verdict-only ablation on matched candidates would be needed to separate these mechanisms.

\section{Discussion}
\label{sec:discussion}

\paragraph{Persistent errors do not establish invariance.} Every tested configuration retains
oracle-relative false accepts. None of the original false-accept contrasts meets the registered
joint decision rule, but this does not establish equivalence or an inability of stronger models
to help. Several LiveCodeBench estimates favor stronger verification roles. Counts of false
accepts and the fraction of accepted claims that are false also answer different questions:
changing the number and composition of accepted outputs can change the latter without a
corresponding count reduction. The result is evidence of residual error under these policies,
with uncertainty about its reduction, rather than a general law about verifier strength.

\paragraph{Feedback and selection change together.} Larger suites, more completed cycles, and
higher oracle pass rates in the primary LiveCodeBench judge cells are consistent with useful
reviewer feedback. However, assigning a stronger judge changes test acceptance, code review,
failure analysis, and subsequent candidates simultaneously. These experiments do not isolate
feedback as the causal source of the gains, nor separate improved generation from improved
selection. The effect also varies across settings: the RGRBench judge rejects many packages at
RED and reduces correct-output yield, while the Gemini judge-only LiveCodeBench replication does
not reproduce the primary experiment's false-reject reduction. Strong test authors can retry
RED too, so their results do not compare a one-shot author with an iterative judge. Costs and
outcomes must be compared by configuration before recommending an efficient deployment.
% trace: experiments/review_audit/results/ANALYSIS.md (complete matrices);
% experiments/exp007_lcb_asymmetry/results/ANALYSIS.md;
% experiments/exp010_flagship/results/ANALYSIS.md

\paragraph{The review contract matters.} The GREEN judge is instructed to evaluate code against
the generated tests, and receives the task title rather than the full original specification.
The RED judge does see that specification, but uses a scoring rubric that can accept a suite
with a deducted error at the chosen threshold. Consequently, the experiment evaluates stronger
models under a particular test-centered review contract. A passing suite supplies no executed
counterexample to its own omissions, but a reviewer given the original specification could still
identify them. It is not logically impossible for an internal reviewer to reduce false accepts.
This distinction connects the results to the established oracle problem~\cite{barr2015oracle}
and limits of resampling under imperfect verification~\cite{stroebl2026resampling}.
% trace: src/vgap/pipeline/templates/judge/code_against_tests.j2;
% src/vgap/pipeline/templates/judge/test_quality.j2; coordinator.py

\paragraph{A direct missing baseline.} A useful next experiment freezes the final candidates
and their original self-verdicts, then asks a separate reviewer to compare each implementation
with the full original specification. Its accept/reject predictions can be evaluated against
the same held-out oracle without changing the candidates. Comparing specification-aware review
with the current test-centered GREEN rubric would test whether the prompt's information and
objective limit gatekeeping. A separate randomized ablation that withholds reviewer feedback
while preserving verdicts would help isolate coaching. Both should report conditional error,
acceptance, correct-output yield, and cost; neither baseline has been run here.

\paragraph{Specifications and oracles can disagree.} Passing tests is not a proof of conformance
to every requirement, and failing held-out tests is not always evidence of violating the supplied
text. The \texttt{numbers\_to\_words} case exposes this second possibility: the requirements leave
the exception type unspecified while the oracle requires \texttt{ValueError}
(App.~\ref{app:telephone}). This is a specification--oracle contract mismatch, not an established
implementation error. The distinction between verification and validation~\cite{boehm1984vv}
helps frame the problem, but does not identify when every observed disagreement originated.
Clarifying acceptance criteria with human input, as in TiCoder~\cite{fakhoury2024ticoder}, is a
plausible intervention. Its effect on this pipeline remains to be measured. Blinded adjudication
of candidate failures against both requirements and oracle expectations would establish how
much of the reported gap reflects semantic implementation defects.

\paragraph{Implication for builders.} Treat self-test success as an imperfect signal whose
reliability must be measured for the intended task distribution and acceptance policy. Held-out
tests, independently checked specifications, and differential or metamorphic checks can provide
additional evidence, each with its own limitations. The current results justify checking
accepted outputs; they do not show that self-verdicts contain no information, that all stronger
reviewers fail, or that an external test suite is infallible.

\section{Threats to Validity}
\label{sec:threats}

\paragraph{Construct and oracle adequacy.} All correctness labels are relative to the stated
benchmark oracle. Incomplete tests can miss defects, while an incorrect or underspecified oracle
contract can reject behavior allowed by the prompt. HumanEval's base and plus suites are distinct
oracles; the post hoc reporting correction uses complete matrices from each rather than combining
base passes and false rejects with plus false accepts. On RGRBench, the mutation kill rate
characterizes detection of selected mutations, not the probability that the oracle's expected
behavior matches the requirements. Classifying surviving mutants does not provide a semantic
error bound. Positive self-verdicts require passing execution; negative verdicts additionally
include judge rejection, exhausted retries, or failure to produce an implementation. Thus false
rejects are not exclusively cases of faulty tests vetoing otherwise correct code.
% trace: experiments/review_audit/results/ANALYSIS.md (oracle-consistent matrices);
% src/vgap/pipeline/subgraph.py; experiments/exp010_flagship/run_flagship.py

\paragraph{Adapter calibration.} The calibration exercises model-written adapters on
behavior-preserving transformations of reference implementations. It observes no adapter errors
in $13$ retained fixtures, after excluding $5$ fixtures whose deterministic adaptation failed.
These selected cases preserve much of the reference structure and do not cover arbitrary
candidate APIs. The recorded calibration error is a fraction of tests failed, whereas the study's
binary endpoint fails a candidate if any oracle test fails. Zero observed calibration errors
neither gives a zero population error bound nor excludes adapter-caused disagreements in the
experimental runs. Adapter and specification mismatches remain possible contributors to the
application-scale measurements.
% trace: experiments/exp010_flagship/calibration/calibration.json;
% experiments/exp010_flagship/calibrate_adapter.py

\paragraph{Selection and repeated packages.} Model and threshold changes alter both acceptance
and the candidates reaching a usable oracle verdict. Restricting a comparison to packages valid
in both cells does not match accepted candidates; similar throughput would not do so either.
The threshold experiment changes RED and GREEN together, and the $\tau{=}0.50$ follow-up is
adaptive and does not exactly match control acceptance. These are comparisons of pipeline
policies, not estimates of reviewer accuracy on a fixed candidate population. Nominal Wilson
intervals treat package-runs as independent; repeated runs on the same package can be correlated.
The supplementary package bootstrap retains repeats and pairing and leaves broad uncertainty
about the conditional-error contrasts. It describes resampling of these selected packages,
not representative sampling of software projects. Three new threshold points have only one
run per package, limiting interpretation of the operating curve. Retry and difficulty-tier
comparisons are also observational: retrying tasks can be harder before the retry occurs.
% trace: experiments/exp013_tau_sweep/PRE_REGISTRATION.md; run_tau_sweep.py;
% experiments/review_audit/results/ANALYSIS.md (package bootstrap)

\paragraph{Registration and collection deviations.} The authors retained protocols intended to
precede collection, but the public history was reconstructed for release; historical run SHAs
refer to a private working history. The released Git graph alone does not independently establish
the original registration chronology. In exp011, partial runs were deleted and repeated after
provider outages, using a nonempty-implementation inclusion threshold that was subsequently
relaxed. This differs from the protocol's treatment of terminal API errors as failed runs and can
also select on legitimate pipeline abandonment. Without the discarded attempts, the resulting
selection and cost effects cannot be fully reconstructed. Cross-provider findings therefore
refer to retained runs, with this additional limitation.
% trace: PROVENANCE.md;
% experiments/exp011_verifier_generalization/PRE_REGISTRATION.md; DEVIATIONS.md

\paragraph{Conclusion validity.} The original tests dichotomize each problem's repeated outcomes
by majority, while effect floors use mean per-run counts; these are different estimands. Some
registered false-reject and total-error tests and the control-spread adjustment were omitted by
the original runners. The review supplies completed tests and clustered intervals as explicitly
post hoc analyses, with nominal, unadjusted $p$-values. They must not be relabeled as prospective
confirmations. Neither failure of a significance test nor failure to exceed a practical floor
establishes an effect of zero. With small selected task sets, repeated outcomes, and numerous
contrasts, meaningful benefits and harms remain compatible with several comparisons.
% trace: experiments/review_audit/results/ANALYSIS.md;
% docs/STATISTICAL_REVIEW.md

\paragraph{Scope and contamination.} The main interventions keep one implementation-generator
model fixed in one pipeline. All three verifiers are evaluated on the two single-function
subsets; only GPT-5.6 Terra is evaluated on RGRBench. Model aliases and available historical
metadata do not fully identify immutable served snapshots. The LiveCodeBench window postdates
the weak model's documented cutoff and reduces a known exposure risk, but does not establish
that task ideas or variants were unseen. Later verifiers may have encountered the tasks;
exposure could change tests, acceptance, feedback, and candidate selection, so its effect on
conditional error has no established direction. Differences between benchmarks also combine
changes in problem selection, specifications, and scoring contracts with application scale.
The results should not be treated as benchmark-wide rates or a general complexity law.

\paragraph{Artifact and execution limits.} The release supports reanalysis of stored outcomes,
with incomplete historical provider snapshots, request settings, and some execution traces;
exact API replay is not established. Logged costs estimate retained successful calls and can
omit discarded or failed attempts; offline adapter grading also contributes to study spend.
Generated code runs in temporary directories under subprocess timeouts, not a hardened sandbox
with network, memory, and filesystem isolation. Timeout policies differ between self-testing
and the benchmark harnesses. Fresh replication should record these settings and use appropriate
execution isolation.

\paragraph{Anchoring.} The artifact includes canonical-example anchoring variants, but these do
not provide a false-accept comparison sufficient to establish that anchoring cannot help. The
case studies show that covering worked examples can coexist with a held-out failure. A fully
instrumented anchoring ablation with repeated runs remains a separate experiment.

\section{Conclusion}
\label{sec:conclusion}

A self-testing pipeline can accept implementations that fail held-out tests. We measure
that disagreement across selected single-function problems and RGRBench packages, and show
why acceptance, oracle success, and abandonment must be reported together. Frontier
verification leaves residual false accepts in every measured condition, while some
interventions improve oracle success and several false-accept estimates decrease. The
experiments do not establish that verifier strength cannot help or that error rates are
invariant. At application scale, stricter gating reduces correct output, and requirements,
oracles, and adapters add measurement uncertainty.

For builders, passing self-authored tests is useful evidence with an empirically measurable
error rate, not a correctness guarantee. Independent evaluation and explicit verdict
accounting remain necessary to assess that evidence. The released instrument and post hoc
reporting corrections provide a basis for stronger tests of specification-aware review,
feedback mechanisms, and oracle fidelity across more pipelines and generators.

\section{False-accept case studies}
\label{app:cases}

The following HumanEval examples share a pattern: the self-authored suite anchors itself to the
specification's worked examples (the anchoring block of App.~\ref{app:prompts} enforces one
\texttt{test\_canonical\_example} per example), the implementation passes these, and both miss
a behavior that the held-out oracle checks. Three HumanEval false accepts make this pattern
specific: two from the all-weak control and one from the cell with a frontier judge, each accepted
with a top GREEN-judge score. Code and tests are copied exactly from the committed run logs.

\paragraph{HumanEval/32 (\texttt{find\_zero}, control cell).} The spec requests a root of
a polynomial with an even number of coefficients (hence odd degree) under the stated
leading-coefficient assumption. The self-suite tests only the two docstring examples
(\texttt{find\_zero([1,2])} $\rightarrow -0.5$, \texttt{find\_zero([-6,11,-6,1])} $\rightarrow
1.0$). The implementation uses Newton's method starting from \texttt{x=0.0} for $100$
iterations. Newton-from-zero converges on both example polynomials, so the suite passes, but this
is not a general root-finder: when the iteration stalls (\texttt{dfx==0}, and it breaks) or
diverges, it returns a non-root. HumanEval\texttt{+}'s extra polynomials cause exactly
this, and the oracle rejects. The tests only confirm the two points the code was tailored for, not
the full specification.

\paragraph{HumanEval/74 (\texttt{total\_match}, control cell).} The spec returns the list with
the smaller total character count, \emph{and returns the first list if the totals are equal}.
The implementation handles the tie incorrectly: \texttt{if total1 < total2: return lst1} else
\texttt{return lst2}, so equal totals default to \texttt{lst2}. None of the five generated
example tests presents a clear tie---the only equal-total case is \texttt{([],[])}, where
both answers are \texttt{[]}, so the tie branch is never tested. HumanEval\texttt{+} includes
an equal-total pair with different contents; the code returns the second list where the spec
requires the first, and the oracle rejects.

\paragraph{HumanEval/153 (\texttt{Strongest\_Extension}, frontier-judge cell).} Strength is
calculated as (uppercase count) minus (lowercase count); the strongest extension is the one with
the highest value, with ties going to the earliest occurrence. The implementation sets the running
maximum to \texttt{0} at the start and only updates it when \texttt{strength > strongest\_strength}.
This means if every extension has a strength of zero or less, and the strongest is not the first
one, the loop never updates and it ends up returning \texttt{extensions[0]}. The two generated
tests do not trigger this scenario---example~1 is all-negative, but its first element is already
the strongest, so the bug is hidden. As a result, the suite passes, and the frontier judge gave it
a score of $1.0$. HumanEval\texttt{+} provides an all-negative case where the maximum is not the
first, and in that case, the oracle rejects it.

\paragraph{At application scale.} RGRBench also contains oracle-relative disagreements
whose source is the requirements contract. The
\texttt{strong\_judge} run on \texttt{numbers\_to\_words} certifies itself, but the held-out oracle
only passes $20$ out of its $22$ tests; App.~\ref{app:telephone} repeats this false accept
completely. The per-package artifacts (including self-authored tests, the generated package, and
the oracle's result) are committed for all $534$ runs.

\section{An RGRBench requirements--oracle mismatch: \texttt{numbers\_to\_words}}
\label{app:telephone}

The false accept of Figure~\ref{fig:misalignment}, laid out end to end. The pipeline sees only
the requirements below; from them it authors its tests and its implementation, and reports success
once the implementation passes those tests. The held-out oracle is applied afterward and never
enters the loop. The implementation passes the oracle's spelling tests; the observed disagreement is the
exception \emph{type} on the range check. The requirement fixes the message but not the
type, the self-test accepts any \texttt{Exception}, and the oracle demands
\texttt{ValueError}. This example supports an oracle-relative gap, but does not establish
that the agent misread or violated its supplied requirements. The historical input is
retained; silently adding the missing type now would change the evaluated task.

\paragraph{Requirements given to the pipeline.} User-story narratives are omitted; the acceptance

\begin{small}
\begin{verbatim}

## Overview
A number-spelling service turns any whole number from 0 through
9999 into its English words, following everyday conventions:
hyphenated compounds for twenty-one through ninety-nine, no "and"
between parts, and plain spaces between the thousands, hundreds,
and remainder portions.

### US-1: Spelling numbers up to twenty
- AC-1.1: Zero is spelled "zero", and single digits use their
  names, such as "five" and "eight".
- AC-1.2: Ten is spelled "ten", and the teens are single
  unhyphenated words, such as "thirteen" and "nineteen".

### US-2: Spelling two-digit numbers
- AC-2.1: Round tens are single words with no hyphen, such as
  "twenty" and "ninety".
- AC-2.2: Other two-digit numbers are hyphenated tens-units
  compounds: 21 is "twenty-one", 77 is "seventy-seven", and 99
  is "ninety-nine".

### US-3: Spelling hundreds
- AC-3.1: 100 is "one hundred"; the leading "one" is always kept.
- AC-3.2: A hundreds part is followed by the spelled remainder
  separated by a space: 303 is "three hundred three", 555 is
  "five hundred fifty-five", and 115 is "one hundred fifteen".
- AC-3.3: The word "and" never joins the hundreds to the
  remainder.

### US-4: Spelling thousands
- AC-4.1: 1000 is "one thousand" with the leading "one" kept,
  and round thousands follow the same pattern, such as "two
  thousand".
- AC-4.2: The thousands part is followed by the spelled
  remainder: 2400 is "two thousand four hundred", 3466 is "three
  thousand four hundred sixty-six", and an empty hundreds part is
  simply omitted, so 5005 is "five thousand five".
- AC-4.3: The largest supported number, 9999, is "nine thousand
  nine hundred ninety-nine".

### US-5: Rejecting numbers outside the range
- AC-5.1: Negative numbers are rejected with an error whose
  message includes "must be in 0..9999".
- AC-5.2: Numbers greater than 9999 are rejected with the same
  error message wording.
