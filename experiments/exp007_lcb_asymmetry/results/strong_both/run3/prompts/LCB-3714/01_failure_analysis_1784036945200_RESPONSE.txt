test_includes_subsequences_up_to_the_full_array_length — inputs `nums=[2, 1, 3]`, `k=3`; expected `28`, got `12`. There is no mechanical cause: `minMaxSums` is imported and called with the correct signature. The shared root cause is that the implementation counts only subsequences of exactly size `k`, not all sizes from `1` through `k`. Here `n=3` and `math.comb(n - 1, k - 1) = math.comb(2, 2) = 1`. The loop adds each value once to `min_sum` and once to `max_sum`: `min_sum = 2 + 1 + 3 = 6`, `max_sum = 2 + 1 + 3 = 6`, so it returns `(6 + 6) % MOD = 12`. That is only the full-array subsequence contribution (`min([2,1,3]) + max([2,1,3]) = 1 + 3 = 4`) incorrectly distributed among elements, and it omits the singleton and pair contributions that bring the expected total to `28`. The divergent expression is `math.comb(n - 1, k - 1)`: it represents only one fixed subsequence size, rather than summing choices for every allowed size. It also incorrectly assigns every element the same number of minimum/maximum roles; those counts depend on sorted position.

test_maximum_length_and_k — inputs `nums=[1] * 100_000`, `k=70`; expected `736486044`, got `552524929`. This is the same fixed-size-only root cause as above. For each of the `100,000` values, the implementation uses `math.comb(99_999, 69)` for `min_sum` and again for `max_sum`. Thus it computes:
`min_sum = 100_000 * C(99_999, 69)`,
`max_sum = 100_000 * C(99_999, 69)`,
and returns `2 * 100_000 * C(99_999, 69) mod MOD`.
Using `100_000 * C(99_999, 69) = 70 * C(100_000, 70)`, this is not generally the required count; however, because all values are identical, the observed result corresponds to counting only the size-70 contribution, `2 * C(100_000, 70) mod MOD = 552524929`. The required result is `2 * sum(C(100_000, r) for r in range(1, 71)) mod MOD = 736486044`, which additionally includes sizes `1` through `69`. The divergent expression is again `math.comb(n - 1, k - 1)`, which omits all allowed sizes below `k`.
