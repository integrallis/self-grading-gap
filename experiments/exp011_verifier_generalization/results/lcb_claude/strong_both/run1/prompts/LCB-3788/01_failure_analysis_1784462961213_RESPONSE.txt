**test_need_to_skip_negative** — expected 10, got 3
- Input: `[1, 2, -10, 3, 4]`
- Expected: `10` (after deleting `-10`, select `[1, 2, 3, 4]`)
- Trace:
  - `right = 0`: `nums[0] = 1`, `current_sum = 1`, `max_sum = 1`
  - `right = 1`: `nums[1] = 2`, `current_sum = 3`, `max_sum = 3`
  - `right = 2`: `nums[2] = -10`, `current_sum = -7`, `max_sum = 3`
  - `right = 3`: `nums[3] = 3`, `current_sum = -4`, `max_sum = 3`
  - `right = 4`: `nums[4] = 4`, `current_sum = 0`, `max_sum = 3`
- Returns: `3`
- Divergence: The algorithm uses a sliding window that maintains contiguity in the original array. It cannot "skip over" element `-10` to join `[1, 2]` with `[3, 4]` because when it hits `-10`, the window includes all elements from `left` to `right`. The problem requires the ability to DELETE elements and then select a contiguous subarray from what remains. This implementation only finds contiguous subarrays with unique elements in the ORIGINAL array, not in arrays after deletions. This is a fundamental algorithmic misunderstanding.

FIX: The current sliding window approach is fundamentally incorrect for this problem. The problem allows DELETING elements first, then selecting a contiguous subarray with unique elements from what remains. You need a different algorithm: for each possible way of deleting elements, find the maximum sum of a unique-element subarray in the remaining array. A correct approach is to iterate through all possible subarrays of the original array, and for each subarray, check if removing duplicates still yields a contiguous unique-element subarray, or use dynamic programming to track maximum sums considering deletions. The sliding window in the current implementation only works for finding unique-element subarrays without the deletion step.
