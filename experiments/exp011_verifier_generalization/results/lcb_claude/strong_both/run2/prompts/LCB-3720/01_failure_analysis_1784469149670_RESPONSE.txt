### test_node_zero_has_outgoing_edges — expected 5, got -1

**Inputs:**
- n = 3
- edges = [[0, 1, 100], [1, 0, 5], [2, 0, 3]]
- threshold = 1

**Expected:** 5

**What the implementation computes:**

2. Binary search proceeds with left=0, right=2

3. First iteration: mid=1, max_weight=5

   - Graph is built with reversed edges: graph[0] = [2, 1], graph[1] = [], graph[2] = []
   - In canReachZero:
     - out_degree = [2, 0, 0]
     - Node 0 has out_degree=2, which exceeds threshold=1

4. Since canReachZero returned False, left = mid + 1 = 2

5. Second iteration: left=2, right=2, mid=2, max_weight=100
   - Build graph with all edges

     - Node 0 has out_degree=2, which exceeds threshold=1
     - Returns False immediately

6. Since canReachZero returned False, left = 3, which makes left > right, loop exits

7. Returns -1

**Root cause:** The implementation is building the graph in reverse (from destination to source) but then checking the out_degree constraint on the reversed graph. This means it's checking whether nodes in the *reversed* graph exceed the threshold, which is incorrect.

Specifically:
- Line `graph[edges[i][1]].append(edges[i][0])` reverses edges for BFS from node 0
- Line `out_degree[u] = len(graph[u])` counts outgoing edges in the *reversed* graph
- But the threshold constraint should apply to outgoing edges in the *original* graph direction

In this test case, node 0 has one outgoing edge [0,1,100] in the original graph, which is within threshold. However, in the reversed graph, node 0 has two incoming edges (reversed from [1,0,5] and [2,0,3]), making it appear as if node 0 has out_degree=2, violating the threshold incorrectly.

The out_degree check should count outgoing edges in the **original** edge direction (from source to destination), not in the reversed graph used for reachability.
