### Failing Test Analysis

**test_duplicate_id_mentions_in_one_message — expected `[2, 1]`, got `[1, 1]`**
The test uses `events = [["MESSAGE", "10", "id0 id1 id0"]]`. It expects user 0 to be mentioned twice. The implementation incorrectly de-duplicates mentions within a single message. Inside the `MESSAGE` event handler, it initializes a `mentioned_users = set()` and, for each token like `id0`, it checks `if user_id not in mentioned_users` before incrementing the count. When the second `id0` token is processed, user 0 is already in the set, so the second mention is skipped. The final count for user 0 is 1 instead of 2.

**test_simultaneous_offline_and_here_message — expected `[0, 1]`, got `[1, 1]`**
The test uses `events = [["MESSAGE", "20", "HERE"], ["OFFLINE", "20", "0"]]`. The test specification requires that for events at the same timestamp, status changes (`OFFLINE`) are processed before messages. The implementation sorts events only by timestamp using `events.sort(key=lambda x: int(x[1]))`. This does not guarantee a specific order for events with the same timestamp. In this case, the `MESSAGE` event is processed before the `OFFLINE` event. At `t=20`, when the `MESSAGE "HERE"` is handled, user 0 is still considered online, so both users are mentioned. `mentions` becomes `[1, 1]`. The subsequent `OFFLINE` event for user 0 has no effect on the already-counted mentions. The correct behavior is to process `OFFLINE` first, making user 0 offline, so that the `HERE` message only mentions user 1.

**test_complex_scenario_with_unsorted_and_simultaneous_events — expected `[3, 3, 1, 3]`, got `[3, 4, 1, 3]`**
This failure is caused by the same event-ordering issue identified in `test_simultaneous_offline_and_here_message`. The relevant events are `["MESSAGE", "161", "HERE"]` and `["OFFLINE", "161", "1"]`. The implementation processes the `MESSAGE` before the `OFFLINE` event.
